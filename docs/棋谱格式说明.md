# 棋谱格式说明（B 定稿 · 前端已按此实现）

实验二要求「使用 MCTS 构造智能体、具有下棋界面、能记录棋谱，棋谱借鉴围棋 SGF 格式」。
这份文档把格式定死：A / C 只要按下面的字段读写，前后端就能直接对上，不用再等样例。

---

## 一、一局棋的内部数据（JSON）

```json
{
  "version": 1,
  "engine": "mcts",
  "mode": "ai",
  "humanSide": "king",
  "result": "king_win",
  "reason": "王累计吃掉 10 枚大臣，王方获胜。",
  "date": "2026-11-23",
  "blackName": "玩家",
  "whiteName": "电脑（MCTS）",
  "moves": [
    {"side": "king",     "kind": "eat",   "from": 8,  "over": 13, "to": 18},
    {"side": "minister", "kind": "place", "from": -1, "over": -1, "to": 0},
    {"side": "minister", "kind": "move",  "from": 22, "over": -1, "to": 26}
  ]
}
```

| 字段 | 取值 | 说明 |
|---|---|---|
| `version` | `1` | 预留，格式变了再 +1 |
| `engine` | `rule_based` / `mcts` | 这局用的是哪个算法（下拉框选的） |
| `mode` | `ai` / `ai-king` / `human` | 电脑执大臣 / 电脑执王 / 真人双人 |
| `humanSide` | `king` / `minister` / `null` | 真人双人时为 `null` |
| `result` | `king_win` / `minister_win` / `draw` | 用两个下划线词，方便脚本统计 |
| `reason` | 任意文本 | 终局原因，原样进 SGF 的 `C[]` |
| `date` | `YYYY-MM-DD` | 对局日期 |
| `blackName` / `whiteName` | 任意文本 | 王方 / 大臣方 |
| `moves[].side` | `king` / `minister` | 王先走，所以第 1 手固定 `king` |
| `moves[].kind` | `place` / `move` / `eat` | 大臣添子 / 平移 / 王跳吃 |

走法字段的三态：

| kind | from | over | to |
|---|---|---|---|
| `place` | `-1` | `-1` | 落点 |
| `move` | 起点 | `-1` | 终点 |
| `eat` | 起点 | 被吃的大臣 | 落点 |

点号 `0..36`，与 `core/board.py`、`static/js/board_data.js` 的节点下标是同一套，
不要另外编号。

## 二、SGF 文本

借围棋的骨架：`GM/FF/CA/AP/SZ/GN/DT/PB/PW/RE` 做头，每手一棵 `;B[] / ;W[]`。
但**走法值不用围棋的 `aa`/`bb` 坐标**——棋盘是 37 个不规则点，硬映射到 19×19
反而读不懂。改成带类型前缀的点号：

| 写法 | 含义 |
|---|---|
| `P18` | 大臣放子到 18 号点 |
| `M16-21` | 走子 16 → 21 |
| `E8-13-18` | 王从 8 跳过 13 落到 18 |

导出样例（`static/js/sgf.js` 的实际输出）：

```
(
GM[1]FF[4]CA[UTF-8]AP[TigerSheep:2.0]SZ[37]GN[国王与大臣棋]DT[2026-11-23]
PB[玩家]PW[电脑（MCTS）]RE[B+]AN[mcts]RU[ai]C[王累计吃掉 10 枚大臣，王方获胜。]
;B[E8-13-18];W[P0];W[M22-26])
```

- 王执黑 `B`，大臣执白 `W`；`RE[B+]` 王胜、`RE[W+]` 大臣胜、`RE[0]` 和棋。
- 扩展属性：`AN[]` 引擎名、`RU[]` 对局模式、`C[]` 终局原因。
- **一个文件可以放多局**（SGF 本身就是游戏集合格式），多局就是多个括号并列：

```
(;GM[1]...;B[E8-13-18])(;GM[1]...;B[M8-12];W[P0])
```

实验二要求的「每小组至少 10 局」直接点一次「导出全部棋谱」就是一个 `.sgf` 文件，
里面 10 棵树。

## 三、前端已经做完的部分（B）

1. **算法下拉**：顶栏「算法」选 `Alpha-Beta` / `MCTS`，随 `/api/ai` 一起把
   `engine` 传给后端；`/api/ai` 返回的 `engine` 会回显，用来确认真的切过去了。
2. **棋谱侧栏**：每落一子追加一行（序号 + 王/臣 + 走法），点任意一行棋盘回看当时的局面，
   回看期间禁止落子，点「回到当前」继续下。悔棋会把对应行一起删掉。
3. **自动存档 + 导出**：一局结束自动存进 `localStorage`（键 `tiger_sheep_archive_v1`），
   「导出本局」出一局，「导出全部棋谱（N 局）」出整库。文件名带时间戳。
4. **导入回放**：选一个 `.sgf` 文件，前端按 JSON 里的规则逐手校验合法性再回填，
   不合法就停在第一个错手并提示是第几手。导入后自动切「真人双人」，防止 AI 抢手。

代码位置：

| 文件 | 内容 |
|---|---|
| `static/js/sgf.js` | SGF 编解码（`moveToToken` / `gameToSGF` / `parseSGF`），不依赖其他模块 |
| `static/js/game.js` | 棋谱侧栏、回放、存档、导入导出（`renderRecords` / `showReplay` / `archiveGame` / `importText`） |
| `static/js/api.js` | `API.ai(state, engine)` 把引擎名带进请求 |
| `templates/index.html` | 「算法」下拉、棋谱栏、导出/导入按钮、`file-input` |
| `static/css/style.css` | 三栏布局（棋盘 / 棋谱 / 信息），1120px 与 860px 两档响应式 |

## 四、给 C 的接口约定

`/api/ai` 的请求体已经支持多带一个 `engine`：

```json
{"state": {...}, "engine": "mcts"}
```

- 不传就用 `TIGER_ENGINE` 环境变量 / 默认 `rule_based`；
- 传了不在 `engines/` 里的名字，`app.py` 直接回 400
  `没有这个引擎：xxx（可选 rule_based / mcts）`，不会进线程池；
- 返回的任务结果里带 `engine`，值是实际用的引擎名。

`/api/records` 现在**不是必需**了：前端已经用 `localStorage` + SGF 导出兜住了
「至少 10 局棋谱」这条要求。如果后面要做「五组 50 局汇总给第三次作业训练」，
再按第一节的 JSON 结构落一个 `records/*.json` 就行，字段不用改。

## 五、别的组发来的棋谱（2026-11-23 实测）

另一组发来 10 局 `.sgf`，用的是同一张 37 点棋盘、同一套点号，但走法值写成冒号式：

| 他们的写法 | 等价于我们 | 含义 |
|---|---|---|
| `P:20` | `P20` | 大臣放子到 20 |
| `S:08:04` | `M8-4` | 走子 8 → 4（两点补零占位） |
| `J:08:18:13` | `E8-13-18` | 王从 8 落到 18，吃掉中间的 13 |

`J` 的字段顺序是 **起点-落点-被吃**，和我们的 `E`（起点-被吃-落点）正好相反。
`sgf.js` 的 `tokenToMove` 遇到 `J` 会自己换位，所以他们的 `.sgf` 拖进界面就能直接回放，
不用先转换。

实测（用 `core/rules.py` 逐手重放）：10 局共 1106 手**全部合法**，说明点号与邻接关系两边一致。
只有 5 局的胜负对不上：他们那 5 局在第 30 手就判「大臣胜」，我们的规则看王还有 1 条斜线可逃
（对方 `RU[KM37-orthogonal-v1]`，王只能走正交线）。汇总训练数据时要么先统一规则，
要么把这 5 局按「未终局」标注，别直接当大臣胜用。
